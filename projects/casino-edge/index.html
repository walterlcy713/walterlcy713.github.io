The context

A Go-based table-game platform supports game state, dealer controls, displays and reporting. I am responsible for keypad updates and integration, developed the USB driver, and share dealer-app updates with a dashboard/web developer. My contributions also include shared development of LED-control integration.

A modular dealer-keypad framework

Dealers use Stream Deck and StreamDock keypads to display game state, enter results and manage table settings. I built a shared interface for device input, button images and layouts, so both device families use one set of keypad logic.

I also implemented text-icon fallbacks: when an image asset is missing, the app generates a labelled icon so the affected button’s function remains identifiable.

Supported game families include baccarat, blackjack, poker, roulette and sic bo, with bonus and jackpot variants; supported variants continue to be added. Keypad functions include staff-ID and PIN login, result entry, closing a table, invalidating the current or previous round, and managing trend-board settings such as minimum and maximum bets.

I maintain and extend the keypad’s handling of updates from multiple backend WebSocket connections concurrently. These connections support the company’s existing systems and new features, with additions contributed by me and colleagues. I am responsible for integrating the updates into the keypad application.

I refactored duplicated keypad code into shared modules and centralised state management to make new game variants easier to add. The shared modules became the basis for additional variants and reduced debugging time.

I also created AI-assisted developer documentation as a reference for colleagues covering my work during leave.

The vendor library, and why I replaced it

In the first version, I integrated the vendor’s C++ SDK into the Go keypad through cgo, combining hands-on coding with AI assistance.

The official StreamDock SDK did not provide disconnect detection. To cover that gap, I added separate HID detection in the keypad application. The SDK and the extra detection path could report conflicting device information.

I used USB protocol reverse engineering to develop a Go StreamDock driver, guiding implementation through an AI-assisted workflow. USB captures taken with usbmon helped map the device communication. The driver replaced the vendor SDK in production and resolved the disconnect-checking conflict.

The Go driver retained the vendor SDK’s functionality and added control of the StreamDock’s own LED strip, including new light effects. This device lighting is a separate feature from the co-developed Arduino table-light integration described below.

Table lights

A colleague and I co-developed the first version of the Arduino control software. I then added the game-state → light-state mapping connected to the Go service, along with new LED effects. I tested the complete keypad → game state → light state control flow before handing the work back to the same colleague for follow-up development. My work also included implementing and testing BlinkStick control and its game-state integration.

Dealer app

The Windows touchscreen dealer app evolved from the dealer UI within an existing dashboard. It hosts a React-based web interface using Microsoft Edge WebView2 and shares the keypad’s backend and game-state data, with its own touch interface covering most keypad functions.

I restructured the app and connected it to the backend’s existing device-registration flow. At startup, the app retrieves device information, identifies its registered device and loads the associated table data, replacing manual table selection. I also added or updated UI and dealer-control functions, and added magnetic-stripe card login alongside staff ID and PIN by integrating a colleague’s card-reading service.

I guided AI implementation of my dealer-app changes and continue updates together with a colleague responsible for the dashboard/web interface. The app is being prepared for on-site deployment.

Configurable approval controls

I integrated the keypad and dealer-app clients with the company’s shared authentication system, handling JWT login, token validation and expiry. I also integrated the existing RFID and magnetic-stripe card login services; the underlying authentication system was developed by colleagues.

I implemented the keypad and dealer-app approval flows, including PIN verification. Operations requiring approval must be confirmed by a different account with a supervisor-level role or above.

The keypad reads per-operation approval settings from the dashboard to determine when approval is required. I integrated this behavior and contributed to the settings UI; colleagues implemented the original web UI and backend checks.

Outcome

The keypad and Go driver are in production across multiple venues. The dealer app is being prepared for on-site deployment. I continue to maintain and update the keypad and dealer app.

To address the dependencies involved in building and installing the device-control tools, I introduced Bazel into the company project through AI-assisted configuration, following a colleague’s suggestion. Initially used for the keypad and related tools, Bazel was later used by other developers for additional components in the same project.
